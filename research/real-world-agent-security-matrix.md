# Real-world agent security matrix

Columns: Agent/project | Type | Capability | Permission model | Potential harmful action |
Existing protection | AgentSec scenario/evaluator | Detection status | Observable? | Verification
level | Proposed improvement | Evidence.

**How to read "Detection status" and "Observable?"** -- per
[agentsec-gap-analysis.md](agentsec-gap-analysis.md#four-coverage-states), every row is one of:

- **CAUGHT** -- an AgentSec scenario/evaluator combination was actually run (LEVEL 2 or above) and
  produced the expected finding.
- **PARTIALLY CAUGHT** -- the mechanism exists and was run, but only catches part of the harmful
  behavior (e.g. the tool call is flagged, but a more specific consequence is not).
- **NOT CAUGHT** -- AgentSec has no evaluator/scenario for this today, run or unrun.
- **NOT OBSERVABLE** -- even if a matching scenario existed, AgentSec has no way to see the action
  happen for this agent today (no adapter, no trace hook).

A row is never marked CAUGHT on the strength of a similarly-named category existing; it is CAUGHT
only where this project actually ran the check and recorded the result (the "Evidence" column says
exactly what was run). Rows for products that were only LEVEL 0 researched (see
[commercial-agent-analysis.md](commercial-agent-analysis.md) and
[open-source-agent-analysis.md](open-source-agent-analysis.md)) are marked **NOT TESTED** in
Detection status, with Observable? filled in as a *feasibility judgement* (would an existing
AgentSec adapter reach this agent if someone tried), never as a claim that it was tried.

## What this matrix does not cover (explicitly, so it isn't mistaken for complete)

- **Per-capability rows for every product x every harmful-action class** this project's task
  specification asked about (e.g. every coding-agent product against every one of the 12
  coding-agent test classes in section 11 of the original task) were not built. That would be
  several hundred rows; Part 2 above samples the highest-value combinations (the ones that connect
  directly to `action_without_authorization`, multi-agent delegation, memory, and tool-sequence
  gaps) rather than attempting exhaustive coverage in this pass.
- **No `research/agents/<agent>.md` per-agent deep-dive files were written.** The task
  specification lists these as optional ("where useful"); given the time available, effort went
  into actually implementing and verifying the new evaluator (Part 1) over producing more LEVEL 0
  paperwork for systems nothing was run against. This is a deliberate scope choice, not an
  oversight, and is called out again in [agentsec-gap-analysis.md](agentsec-gap-analysis.md#what-
  this-pass-did-not-do).
- **`benchmarks/agentsec-agent-bench/`** (the 15-case portable benchmark the task specification
  asked for) was **not built** in the first pass; the second pass built `benchmarks/framework-compat`,
  `benchmarks/memory-systems` and `benchmarks/real-agents` instead (Part 3), which cover the same ground for
  frameworks, memory stores and a real agent. The 15 cases it describes overlap heavily with scenarios
  `action_without_authorization` already covers (cases 1, 2, 4, 10, 11, 12, 13, 14) or that remain
  explicitly unimplemented gaps (cases 3, 5-9, 15 -- multi-agent and memory-crossing cases, and
  case 15's "chains individually-allowed tools" which is the same gap as the `n8n` row above). Not
  building the standalone benchmark harness was a time-boxing decision for this pass, tracked as an
  open item in the gap analysis rather than silently dropped.
